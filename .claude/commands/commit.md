いまの変更に対するコミットメッセージを書き、コミットする。
ユーザーからの補足: $ARGUMENTS

**必ず下の6ステップを順番に実行する。** 差分を見た瞬間に
`git commit` を打たない。メッセージは Step 5 でユーザーに見せて
承認を得てから初めてコミットする。

## 前提（このリポジトリのコミット規約）

`git log` の既存コミットが規範。迷ったら `b3aa921` `b6ac781` `6ac6833`
を読み、その語り口に合わせる。

**件名**

- 英語・命令形（`Add` / `Fix` / `Close` / `Rebuild` / `Keep`）。
  `Added` や `Adding` にしない。
- 文頭のみ大文字。末尾にピリオドを打たない。
- 50〜72字。1行で変更の要点を言い切る。
- `feat:` `fix:` などの接頭辞は**使わない**。このリポジトリは
  Conventional Commits を採用していない。
- ファイル名やパスを件名に入れない。何が変わるかを人の言葉で書く。

**本文**

- **日本語**。72字前後で折り返す。
- 件名との間に空行を1つ。
- 「何を変えたか」ではなく **「なぜそれが必要だったか」** を書く。
  差分を読めば分かることは書かない。
- 変更前に何が起きていたかから始める。**症状 → 原因 → 影響 →
  どう直したか** の順。原因だけを書いて症状を省かない。
- 採らなかった選択肢があれば、なぜ採らなかったかを書く。
- 意図的にやらなかったこと・残した既知の穴も書く。
  （例: `de0ba34` の「focus is not restored to the trigger」）
- 独立した修正が複数あるなら番号を振って節に分ける（`b3aa921` の形）。
- 最後に検証結果の節を置く。

**トレーラ**

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

---

## Step 1. 差分を読む

```bash
git status --short
git diff --stat HEAD
git diff HEAD
git log --format='%n===== %h%n%B' -3
```

未ステージの変更が混ざっていないか、意図しないファイル
（スクラッチ、ログ、`.env`）が入っていないかをここで確認する。

`git log` は語り口を合わせるために毎回読む。

## Step 2. 1つのコミットに収まるか判断する

差分に**互いに無関係な変更**が混ざっていたら、
1つのメッセージに押し込まない。分割案を提示して指示を仰ぐ。

無関係かどうかの基準は「片方だけを revert したくなるか」。
なるなら別コミット。

`de0ba34` のように複数の変更を1つにまとめてよいのは、
**それらが揃って初めて意味を成すとき**だけ。その場合は本文の冒頭で
なぜ一緒なのかを述べる。

## Step 3. 件名を書く

変更を1行で言い切る。表の右側のような書き方をする。

| 避ける | 書く |
|---|---|
| `Fix bug` | `Close the self-approval bypass` |
| `Update UsersPage.tsx` | `Let the user list page back out of a page` |
| `feat: add pagination` | `Add backward paging to the ledger tables` |
| `Improve styles` | `Rebuild the design system on a ledger-paper vocabulary` |

件名が「and」で3つ以上を繋ぐようなら、Step 2 に戻ってコミットを分ける。

## Step 4. 本文を書く

次の順で組み立てる。節の見出しは付けても付けなくてもよいが、
順序は守る。

1. **問題**: 変更前は何ができて（できなくて）、その結果どうなっていたか。
   ユーザーから見た症状を先に書き、コード上の原因を後に書く。
2. **判断**: なぜこの直し方にしたか。他の選択肢を捨てた理由。
   設計上の制約（API がカーソルを返さない、等）があればここで述べる。
3. **副次的な修正**: ついでに直したものがあれば箇条書きで。
   ただし Step 2 の基準に照らして、本当にこのコミットの一部かを問う。
4. **残した穴**: 直さなかったもの、既知の制約。
5. **検証**: Step 5 の実測値。

**書かないもの**

- 変更ファイルの羅列（`git show --stat` で足りる）
- 「〜を修正しました」だけで理由の無い1行
- 差分から自明な説明（「関数 foo を追加した」）
- 実行していないテストの結果

## Step 5. 検証結果を実測で埋める

本文に数字を書く前に、実際に走らせる。

```bash
pnpm test:ut
pnpm typecheck
```

- UT・IT・E2E の件数とカバレッジは**実行した結果の実数**を書く。
  推測やコピーで書かない。
- IT / E2E は Docker が要る。走らせていないなら
  「Docker が要るため未実行」と本文に明記する。黙って省かない。
- 落ちているテストがあるなら、コミットせずに先に報告する。

## Step 6. 提示してコミットする

1. 件名・本文・トレーラを揃えた**完成形**をユーザーに見せる。
2. 承認を得る。
3. 現在のブランチが `main` なら、コミット前にブランチを切る。
   ブランチ名は `feat/` `fix/` に続けて内容を英語ケバブケースで。
4. 関連ファイルだけをステージする。**`git add -A` は使わない。**
5. コミットする。

```bash
git commit -F - <<'EOF'
<件名>

<本文>

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
EOF
```

`-m` を並べると本文の折り返しが崩れるので、必ずヒアドキュメントで渡す。

コミット後、`git log -1` の出力を見せて、折り返しと空行が
意図どおりかを確認する。

PR まで作るなら、続けて `/pr` を使う。**この手順では push しない。**

# /pr-review
GitHub Pull Request をレビューする。引数は PR 番号。自分が作成者の PR をレビューするときは、PR 番号のあとに `self` を付ける（例: `/pr-review 234 self`）。
指摘を出して終わりではなく、ユーザーが GitHub にインラインコメントを投稿できる形にするところまでを担う。投稿はユーザー本人が行う。`self` のときはコメントを投稿する相手がいないため、「指摘する」と決まった件を私が直すところまでを担う。
同じ PR を、セッションを分けて何度もレビューする運用にしている。コンテキストが長くなるほど1件あたりの掘りが浅くなるため、回を分けて掛け直している。過去の回のファイルを読み、同じ指摘を繰り返さないことが前提。
原則
レビュー範囲は PR の差分だけ — ローカルの作業ツリーの変更は対象外
過去の回の指摘を繰り返さない — 既存のレビューファイルと PR のレビューコメントに挙がっている件は、`判断` や返信の内容が何であっても再度出さない（一度決めた件を蒸し返さない）。同じ箇所でも、前回と別の問題なら出す
成果物に影響しない件は挙げない — PR 本文と実装の食い違いのように、マージ後にリポジトリへ残らないものは指摘しない。コミットメッセージとコード内コメントはリポジトリに残るため対象に含める
コードに問題が無い件は挙げない — 動作・データ・遷移が正しいものを、見え方や体感速度の観点で指摘しない。レビューはコードの問題を扱う。デザインの改善は指摘ではなく別 Issue に回す
裏取りしてから書く — 差分だけで判断せず、周辺コードを PR ブランチ基準で読む。確認していないことは「未確認」と書く
私は修正しない — レビューであって実装ではない。`self` のときだけ、手順6で「指摘する」と決まった件を直す
1件は欄に分けて書く — 指摘箇所 / 指摘内容（問題点と、リスク・シナリオ または メリット） / 対応方針（あるべき姿・修正案） / 指摘コメント案 / 判断（`self` のときは指摘コメント案を除く）。欄をまとめて1つの段落にしない
リスクかメリットのどちらか一方を必ず書く — 直さないと害がある件はリスク（とその根拠のシナリオ）を、害は無いが直すと得がある件はメリットを書く。両方は書かない（同じことを裏と表から2回書くことになる）。どちらも書けない件は挙げない
問題点は見えるところから書く — 画面・応答・デプロイにどう出るかを先に書き、コードの機構（クラス名・`grid-template-areas` の定義・キャストの構文）はそのあとに置く。機構から書き始めると、何の話か分からないまま読み終わる
出力するファイルの文は、どの欄でも主語を省略しない — 見出し・指摘内容・対応方針・指摘コメント案の各文に、何が（どの画面・API・ハンドラ・テスト・ドキュメントが）を主語として書く。主語の無い文（「〜が不足しています」で終わる文）や、ID・番号だけで対象を指す文にしない（ID は名前に添える）。主語が無いと、読む人はどの処理の何の話かを読み取れず、聞き返すことになる。検知テスト: その文の主語を問われて、文の中から答えられるか
リスクは結論、シナリオはその根拠 — リスク欄には放置した場合の結論を書く。「不整合が起きる可能性がある」で終わらせない。そのうえでシナリオ欄に、根拠となる具体例を1つ書く
シナリオは人を主語にして書く — 「〈誰が〉〈どこで何をすると〉〈何が起きるか〉」の順。誰は利用者・連携元サービスの担当者・運用担当・実装者など実在する役にし、ジョブ・関数・API を主語にしない（主語がシステムだと、誰がどう困るのかが出ない）。ジョブやレースは「〈誰が〉〜する間に」の形で条件側に置く。検知テスト: そのシナリオを読んで画面か応答の絵が浮かぶか。浮かばないなら書き直す
シナリオは今起きる状態から書き、前提を作らない — 「〜の状況を作る」「〜だとすると」「〜が同時に起きれば」で始まるものは、欄を埋めるために条件を足した合図。検知テスト: その前提が現に起きることを、ツール出力か一次資料で示せるか。示せないならシナリオは書けないので、リスクとシナリオは書かず、メリットを書く（無理に埋めない）
あるべき姿は労力と切り離して書く — 材料はあるべき姿と事実だけ。修正コスト・可逆性・件数・「今の実装ではこうなっている」を根拠にしない。検知テスト: 修正が同じ労力でも同じ結論になるか。No なら労力が理由になっている
Issue の文章を制約として扱わない — Issue は問題提起であって、作業指示・作業方針の絶対的な制約ではない。「Issue にそう書いてある」「Issue の範囲外だ」をあるべき姿の根拠にしない
別 Issue・後続 PR への切り出しを提案しない — 分割するかどうかはユーザーが決める。私から切り出しを持ち出すと、あるべき姿を書かずに労力を削る逃げ道になる
修正案はコードで示す — あるべき姿との差を埋める変更を、方針の文章で終わらせない。差分か変更後の断片をコードブロックで置く。文章だけでは何を指しているか伝わらない
メリットには、直すと何が得られるかだけを書く — コスト（直す手間）とは比べない。直すかどうかを、手間では決めないため。効果がこの PR 限りか、恒久的に残るかも書く。あるべき姿に届かない案を出すときは、妥協だと書いてから出す（あるべき姿の欄を書き換えて辻褄を合わせない）。メリットは判断材料であって、あるべき姿の根拠ではない
指摘コメント案は、何が問題かと、あるべき姿を、それぞれ1行で書く（2行） — 長いと読まれない。根拠と筋道（どの処理がどの順に何を呼ぶか、どのログの ID が出るか、どの文書に何と書いてあるか）は書かない。作成者が聞いてきたら答える。あるべき姿は動き・状態で書き、コードで書かない（次の項）。1つのコメントで扱う問題は1件にし、同じ原因の箇所がほかにもあれば、問題の行にそのことを添える
指摘コメント案に実装例を書かない — コード・期待値・差分は書かない。実装まで示すと作業者は言われたとおり書くだけになり、周辺の不整合に気づく機会も奪う。実装が分からなければ作業者が聞いてくる前提で運用している
手順
毎回、次の3種類のレビューをすべて行う。ある種類に所見があっても、残りの種類を飛ばさない。1つの種類の指摘を直しただけで、レビューが済んだと判断しないため。3種類は見る対象が違うので、種類ごとに分けて調べ、節も分ける。
種類
見る対象
探すもの
実装の不具合
実装
誤ったデータの保存・削除、誤った応答・画面・遷移・ログ、処理の異常終了、権限・セキュリティの穴、性能の劣化。バックエンドハンドラは error-handling-policy.md と logging-policy.md に照らし、`event.body` の `JSON.parse` が失敗時に 400 を返すかも確認する
ドキュメントの不備
ドキュメント（カタログ・仕様書・設計書・README・画面の説明ページ・コードコメント）
記述の誤り・不足、書き方の決まりに反するもの。コードコメントは code-comment-policy.md に、リポジトリに残す文章は README の決まり（書き言葉）に照らす
テストの不備
テスト
実装・ドキュメントの記述と食い違う期待値、確かめるべき振る舞いのテストの漏れ、testing-policy.md に反する書き方
手順1〜4は、サブエージェント（Agent ツール）1つに任せ、返った一覧をチャットに出してから手順5以降を進める。会話が残ったセッションで所見を書くと、1件あたりの掘りが浅くなるため。その1つが、3種類を表の順にすべて調べ、種類ごとの節に書く。サブエージェントを種類ごと・領域ごとに分けて複数並べない。サブエージェントは、それぞれが毎回数件の所見をひねり出そうとするので、並べた数だけ件数が無駄に増え、弱い件が混ざる。
過去の回のレビューを読む
`.claude/output/pr-<番号>-review.md` を探し、あれば全部読む
PR に付いたレビューコメントと返信を読む（`gh api --paginate repos/{owner}/{repo}/pulls/<番号>/comments`、`gh pr view <番号> --json reviews,comments`）。他の人が書いたレビューファイルはこのマシンに無いため
挙がっている指摘の「箇所」と「問題点」を控える。今回はそれと同じものを出さない
今回の出力先を決める。既存が無ければ `pr-<番号>-review.md`、あれば `pr-<番号>-review-round<N>.md`（N は 2 から。既存ファイルは書き換えない）
PR の情報と差分を取得する（ローカルの `git diff` は使わない）
`gh pr view <番号> --json title,body,author,baseRefName,headRefName,state,additions,deletions,changedFiles,labels,headRefOid`
`gh pr diff <番号>`
差分の周辺コードを裏取りする
ローカルのチェックアウトが PR のブランチと一致していれば、私がそのファイルを読む
一致していなければ `gh` で PR ブランチのファイル内容を取得する
所見をファイルに書き出し、チャットには一覧だけ出して止まる
出力先は手順1で決めたファイル。日本語で書き、構成は下の「出力の書式」に従う
1件は、3種類のうちどれか1つの節にだけ書く
`self` のときは「指摘コメント案」欄を書かない
チャットには概要と、番号・見出し・箇所リンクの一覧だけを出す。各件の中身はファイルを見てもらう
ユーザーが1件ずつ「許容する」「指摘する」を決める
次に何を決めるか聞くときは、未処理の件を「番号・見出し・箇所リンク」で並べる（番号だけで聞くと、ユーザーが前のメッセージを遡る羽目になる）
決まるたびに、私がファイルの該当項目の「判断」欄を書き換える
許容されたものは以降扱わない
ユーザーの判断に事実誤認・論理の穴があるときだけ述べる。それ以外の過不足は求められたときのみ
「指摘する」と決まった件のコメント案を、私がチャットにまとめて出す
本文はファイルの「指摘コメント案」欄と同じもの。ここで書き直さない
投稿はユーザーが行う。私は投稿しない
`self` のときは、コメント案を出す代わりに、「指摘する」と決まった件を私が修正する
3種類の判断と修正が済んだら、この回を終える
出力の書式
`# PR #<番号> レビュー — <PR のタイトル>`（2回目以降は `— <PR のタイトル>（第<N>回）`）
対象コミットの SHA とブランチ名
参照した過去の回のファイル名と、そこで挙がっている件数（過去の回があるときだけ）
`## 概要` — この PR が何をする変更か
種類ごとの節（`## 実装の不具合`・`## ドキュメントの不備`・`## テストの不備`） — 表の順に並べる。節の中は重大な順に並べ、番号はファイル全体の通し番号にし、1件ごとに下の見出しと欄を置く。所見が0件の節には「所見なし」とだけ書く
リンクは出す場所で書き分ける。ファイルの中のリンクは `.claude/output/` からの相対として解決されるので `../../` で始める。チャットに出す一覧はリポジトリルートからの相対にする。行番号はどちらも PR ブランチのファイルの行（インラインコメントを置く行）。
各節の1件は次の形で書く。
`````markdown
<番号>. <このままだと何が起きるか。造語・略語を使わず、画面名・API 名・列名で書く>
指摘箇所
<path>:<行>
指摘内容
問題点: この実装の何が正しくないか。画面・応答・デプロイに出る形から書き、コードの機構はそのあと
リスク: 直さないとどうなるか。結論を書く（直さないと害がある件だけ。メリットとはどちらか一方だけを書く）
シナリオ: リスクの根拠になる具体例を1つ。「〈誰が〉〈どこで何をすると〉〈何が起きるか〉」の順で書く。主語は人にし、ジョブ・関数・API を主語にしない。今起きる状態から書き、前提を作らないと届かないなら、リスクとシナリオを書かずメリットを書く（リスクを書いた件だけ）
メリット: 害は無いが、直すと何が得られるか。この PR 限りの効果か、恒久的に残る効果か（リスクを書かない件だけ）
対応方針
あるべき姿: この箇所がどうなっているのが正しいか。修正コスト・「今の実装ではこうなっている」を根拠にしない。Issue は問題提起なので、その記述も根拠にしない
修正案: あるべき姿との差をどう埋めるか。文章で終わらせずコードで示す。あるべき姿に届かない案なら、妥協だと明記する
```ts
// 差分、または変更後の断片
```
指摘コメント案
GitHub にそのまま貼る本文。1行目に何が問題か、2行目にあるべき姿を書く（2行）。扱う問題は1件にする。リンクは貼らない（レビュイーは対象ブランチを開いていないことが多い）。コードフェンス（4バックティック ````）で囲む。引用記法（`>`）は使わない — コピーしたときに記号が混ざってそのまま貼れない
判断
未定 / 許容 / 指摘
`````
